# NFSU2 in the Marquinhos Discord Activity: feasibility research

Research date: 2026-11-13. Scope: the local MarquinhosBOT and nfsu2-web checkouts and first-party platform documentation. This is an architectural assessment, not a successful end-to-end test. Repository links describe the checked-out working trees, which may change.

## Decision

An Activity integration is plausible, but the decisive question remains open: can the actual Discord Activity frame, through Discord's production proxy, run nfsu2-web's shared-memory WebAssembly workers and WebGPU? The game will not start without these capabilities. Start with a capability probe and a real game boot before investing in the lobby or production integration. An external-browser launch coordinated by Marquinhos is a practical fallback if the embedded runtime fails.

A noteworthy option missing from the earlier assessment is [Document Isolation Policy](https://developer.chrome.com/blog/document-isolation-policy), introduced in desktop Chrome 137. It can isolate an individual frame and enable shared memory without the usual COOP/COEP requirement on the whole frame chain. This is a candidate to investigate, not proof that Discord's client, permissions policy, proxy, workers or deployed Chromium version support the combination. [Recent Web Platform Tests](https://chromium.googlesource.com/external/w3c/web-platform-tests/+/refs/tags/merge_pr_64265) changed expected permission behavior; that change does not establish support in a particular Discord build. An older [Discord SDK issue](https://github.com/discord/embedded-app-sdk/issues/194) reported SharedArrayBuffer unavailable in Activities, before this browser feature existed.

## Runtime and embedding

- The [game's startup checks](../../../nfsu2-web/web/src/app/checks.ts#L95) require secure context, cross-origin isolation, SharedArrayBuffer, shared WebAssembly memory, Atomics.waitAsync, SIMD and a usable WebGPU adapter. The [host](../../../nfsu2-web/web/src/host/process.ts#L91) shares memory across workers; [the network worker](../../../nfsu2-web/web/src/net/worker.ts#L34) also checks isolation. A single-thread build would require substantive runtime work; turning off one flag is not an established solution.
- The [game server's headers](../../../nfsu2-web/web/server-rs/crates/headers/src/lib.rs#L45) explicitly prevent framing with `frame-ancestors 'none'` and `X-Frame-Options: DENY`; they also set COOP, COEP and same-origin CORP. An Activity-specific response policy must permit the actual Discord ancestors, while retaining appropriate CSP, WebAssembly and worker permissions. Merely adding a header at the origin does not prove Discord forwards it or allows the feature.
- Test `Document-Isolation-Policy: isolate-and-credentialless` and `isolate-and-require-corp` separately in a test Activity. Inspect the *final response* through the proxy, actual frame policy and console; run the SDK handshake and `postMessage` as well as a real shared-memory exchange. Check workers and AudioWorklet separately. If a nested game iframe is used, test it as nested: parent policy, frame permissions, CSP, source URLs and SDK message bridging can differ from the top-level Activity frame.
- The renderer requires WebGPU and a successful adapter/device request. A normal browser result does not guarantee the same result in Discord desktop's embedded engine. Test desktop Discord for the target operating systems and Discord in each intended browser. Record client/browser versions, GPU, feature status and failure text. Start with desktop; mobile support needs separate evidence for device memory, WebGPU, storage and controls.
- Audio needs an interaction to initialize; keyboard focus, input capture, browser shortcuts, gamepad delegation, fullscreen, resizing, loss of focus and background throttling need actual Discord tests. [Game memory notes](../../../nfsu2-web/web/src/host/memory.ts#L1) report roughly 930 MB used by the guest from menus, separate from other browser/GPU allocations. Measure on the actual builds and hardware.

## Proposed architecture if the probe passes

1. Keep Marquinhos as the Activity entry, Discord identity, party/lobby and user interface. The current [handshake](../../apps/activity/src/platform/discord/auth.ts#L28) obtains user, guild and Activity instance identifiers, and currently rejects launches without a guild.
2. Run nfsu2-web's Rust server as a separate service. It already implements the game's virtual LAN, free-roam hub and Online host; retain that protocol instead of reimplementing it in Colyseus. [Server route overview](../../../nfsu2-web/web/server-rs/src/main.rs#L4).
3. Map a Marquinhos party to an agreed game world and/or race lobby. [Named worlds](../../../nfsu2-web/web/src/app/settings.ts#L646) determine who is visible in free roam; crews are a separate feature. They are explicitly not private access controls. Free roam, the game's Online races and its LAN modes should each be tested independently; a shared Discord room does not automatically create a race or synchronize career progress. The game already supports a [world invite link](../../../nfsu2-web/docs/web/PLAYING.md#L923); its [Online mode](../../../nfsu2-web/docs/web/PLAYING.md#L1050) supports up to six players per race. Free roam requires career progression beyond the prologue.
4. Make a deliberate frontend choice: integrate the game's page/runtime into the Activity document, or host it as a nested document with a narrow message interface. The former needs DOM, CSS, lifecycle, input and SDK integration; the latter needs framing headers, permissions and message validation. Both require isolated runtime and proxy proof. Discord describes the SDK as intended for an SPA and recommends nesting non-SPA frameworks within it; this is guidance, not a guarantee that this game can be nested. [Discord lifecycle documentation](https://github.com/discord/discord-api-docs/blob/main/developers/activities/how-activities-work.mdx).

### Marquinhos changes

- Add an NFS game identifier to the [closed game contract](../../packages/contracts/src/activity/gameId.ts#L3), registry, hub presentation, routes and launch/deep-link flow as needed. The [registry](../../apps/activity/src/games/registry.ts#L22) alone does not provide a working room.
- Decide whether to add a Colyseus control-room adapter to reuse room listing and lifecycle, or build a small dedicated party flow. [Room keys](../../apps/api/src/modules/activity/room-key.ts#L21) distinguish game, mode, Activity instance and room; those identifiers do not automatically bind players to a Rust session. Existing Colyseus tokens do not authenticate the Rust WebSocket.
- Define explicit joining, joining an already-running party, changing games, reconnecting, leaving, Activity close, abandoned lobbies and server restart. Decide whether parties share a world only or also facilitate creating and joining a race. Ensure the SDK handshake and launch parameters survive navigation; avoid initializing multiple SDK connections accidentally.
- Treat client-supplied guild/instance/room identifiers as untrusted for access decisions. The existing API verifies user and guild membership for relevant flows, but review instance verification separately. Discord recommends its [Activity Instance API](https://github.com/discord/discord-api-docs/blob/main/developers/activities/development-guides/multiplayer-experience.mdx) to help validate an active instance. Decide if party membership must be enforced, rather than merely coordinated.

### Routing and networking

The game assumes it owns the origin root: examples include `/game.json`, `/game.wasm`, `/data/*`, `/data-blocks/*`, worker scripts and `/lan`; the latter is explicitly built from the current host in [net/index.ts](../../../nfsu2-web/web/src/net/index.ts#L777). Marquinhos already serves its SPA at `/` and reserves other routes in its [gateway](../../deploy/nginx/activity.conf#L34). Either adapt all game paths to a consistent prefix or carefully route every root endpoint without collisions. Include asset manifests, language files, worker/worklet URLs, service-worker scope, save and auxiliary endpoints—not just the HTML and WebSocket. Check the Vite development proxy and production gateway separately.

Discord [routes Activity traffic through its proxy](https://github.com/discord/discord-api-docs/blob/main/developers/activities/development-guides/networking.mdx), supports WebSockets and uses URL mappings. Explicitly verify final URLs from workers: SDK URL patching in the main document should not be assumed to patch worker globals. Test exact bytes and streaming, MIME types, `Range`/206 and 416 responses, compressed blocks, caching, large/partial downloads and WebSocket upgrades, binary messages, idle duration, disconnect and resume. Check latency and jitter during races with multiple players. Proxy service behavior and limits must be measured through Discord; generic Cloudflare limits are not proof of Discord's proxy configuration.

The Rust server validates Host and request Origin; configure the actual proxy chain and allowed public names deliberately, rather than disabling checks. See [LAN handler](../../../nfsu2-web/web/server-rs/src/app/lan.rs#L105) and [server startup documentation](../../../nfsu2-web/web/server-rs/src/main.rs#L26). Check whether Discord's proxy collapses client IPs and how that affects rate limits, connection limits, bans and logging; never trust a forwarded IP from an untrusted hop. The gateway's [1 MB request limit](../../deploy/nginx/activity.conf#L14) and caching rules need review for the chosen game endpoints, particularly optional save uploads.

## Assets, rights, storage and operations

- Check the existing Discord application's verification and platform settings. Discord's [Activity guidance](https://support-dev.discord.com/hc/en-us/articles/26576097154199-What-are-Verified-and-Unverified-Activities) says unverified Activities are restricted to developers and testers and servers with fewer than 25 members; do not assume the current app is verified or eligible in the intended server.

- [Build requirements](../../../nfsu2-web/README.md#L32): the precise North American v1.2 executable, Python, Node, Rust and the specified WASI SDK are needed to generate the game-derived WebAssembly module. The original game files and generated output are not in source control. Version the server, frontend and module together; verify the executable and asset set; keep game-derived outputs out of the repository and public CI artifacts.
- The supplied [deployment guide](../../../nfsu2-web/web/deploy/README.md#L36) says its server has no accounts or passwords and anyone who can reach it can download game files. The project's MIT license covers its own code; it does not grant rights to distribute the original game, music, or third-party assets. Determine the rights and the intended distribution model before making a shared server available. A private Discord room or obscure world name alone does not protect the assets. Hosting one's own copy for other users still needs a rights determination; do not assume ownership by one participant resolves distribution.
- If restricting access, design authorization for the page, assets, manifests, range requests, optional vault and `/lan`, with short-lived credentials scoped to user and party. Consider cookie partitioning, workers, WebSocket handshakes, retries and expiry. Discord's documentation warns the Activity URL is publicly reachable and provides [cookie requirements](https://github.com/discord/discord-api-docs/blob/main/developers/activities/development-guides/networking.mdx); login UX and access enforcement are separate. Do not put Discord access tokens in URLs or logs.
- Saves and settings use browser storage including OPFS; cloud saves are an optional passphrase-based game feature, not automatically linked to Discord. Test write, reload, Activity restart, quota/persistence, eviction, save export/import, concurrent sessions and cloud conflicts. Discord's origin and browser storage partition may differ from the standalone site, so plan a save migration and backup path. See [saving guide](../../../nfsu2-web/docs/web/PLAYING.md#L463) and [save storage](../../../nfsu2-web/web/src/app/savefs.ts#L21).
- Add a Rust service to the existing deployment with a compatible build/image, read-only game/module mounts, persistent server state, health check, startup behavior, CPU/memory and network limits, log rotation, backups, monitoring, TLS and rollback. [Upstream Compose](../../../nfsu2-web/web/deploy/compose.yml#L24) is a reference with host networking and large-scale settings, not a drop-in replacement for [Marquinhos Compose](../../deploy/docker-compose.yml#L1). Measure memory, CPU, disk, download volume and transfer costs for the actual player count; no reliable budget follows from source alone.
- The checked-out nfsu2-web [README](../../../nfsu2-web/README.md#L1) says public development was archived on 9 November 2026. This integration would maintain its own fork of the public snapshot unless another update path is arranged. Preserve upstream and third-party attribution and review subsequent dependencies and changes.

## Ordered proof and acceptance gates

1. **Capability probe:** use a separate development Discord application and the real proxy, not only a localhost URL override. Compare COOP/COEP and DIP responses; record the final headers, frame and worker isolation, shared-memory construction and transfer, Atomics.waitAsync, SIMD, WebAssembly compilation, SDK handshake, WebGPU adapter/device, OPFS and audio. Discord itself [recommends testing via its proxy](https://github.com/discord/discord-api-docs/blob/main/developers/activities/development-guides/local-development.mdx). Failure of mandatory features stops the unmodified runtime approach; isolate each cause rather than assuming the proxy or Discord is responsible.
2. **Single-player boot:** with authorized game files and matching build, load the actual module and assets in Discord, get to a drive, save, close and restore. Check worker and audio errors, control focus, performance and memory on each target client. Confirm frame/CSP changes do not break the existing Activity.
3. **Networking:** route the real server; test ranges, binary WebSocket and reconnect through the production-like proxy. Two players enter the same named world, see and drive near each other, then complete an Online or LAN race. Check state after network interruptions and different clients.
4. **Party and access:** integrate game selection and room join, derive a world association, enforce any chosen access policy on every relevant endpoint, verify identity/instance server-side where required, and test cross-room isolation and direct unauthorized requests.
5. **Operations:** exercise deployment, health checks, backup/restore, resource limits, update/rollback and observability. Have friends test first-load time, input, sound, latency, saves and recovery. Review distribution rights before expanding access.

The tests above are proposals, not results. This research did not launch the Activity, build the game, inspect the user's Discord application settings, measure the production host, or verify permissions to distribute game content. Discord client versions, final proxy headers, platform availability, effective CSP, performance and deployment costs remain empirical unknowns.
